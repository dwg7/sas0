## What this repo is

sas0 is a project of DWG7 (UN Smart Maps Group), a Domain Working Group of the [UN Open GIS Initiative](https://unopengis.org/). It is a static, zero-build GitHub Pages site — everything served lives under `docs/`, deployed straight from `main`, no bundler, no `package.json`, no build/deploy CI. `scripts/check-links.sh` (D22) is a link-checking maintenance tool run both by hand and, since D45, weekly via `.github/workflows/check-links.yml` — sas0's one CI job, deliberately scoped to link-checking only; it doesn't build or deploy anything.

## Project philosophy — read before adding a data source

- **Open data only, as a hard boundary, not a TODO.** Every instrument here (D11, D15) pulls from data that's already genuinely public — JMA's feeds, GSI's portal, municipalities' own published pages. Never add an authenticated, internal, or otherwise non-public data source to sas0, even if a future maintainer happens to have access to one. This isn't an oversight to eventually fix — see [DECISIONS.md](DECISIONS.md) D17 for why: the open-only scope is itself the point (proving the architecture works from public data, no backend), and a future *internal* service integrating protected data would be a separate, properly access-controlled project, not a mode of this one.
- **When evaluating a new data-source candidate, "open access" and "wants to be aggregated" are two independent axes, not one.** A source can be freely readable (no login) yet explicitly prohibit reuse (news orgs: NHK/北海道新聞's RSS is public but their terms forbid republishing it, and D51's survey found no CORS either) — or reuse-friendly by design yet access-gated (L-Alert, MLIT's 不動産情報ライブラリ API: built for redistribution, but registration/contract is required to reach it). Both fail D17's bar. 気象庁 and 国土地理院 are the rare sources positive on *both* axes (open, no registration, and explicitly built for reuse) — a fairly deep survey (D51: 日赤/道内NPO, L-Alert, MLIT/内閣府, 在札幌各国公館, NHK/北海道新聞) found no third source matching that combination within Hokkaido. Don't assume a new candidate is promising just because it's public *or* just because it looks built for integration — check both.
- **Source-evaluation checklist** — this has been applied consistently (D6, D19, D51, D67) but was never written down until now; run through it for any new data-source candidate before adding it:
  1. **CORS**: `curl -H "Origin: https://dwg7.github.io" <url>` and check for `Access-Control-Allow-Origin`. No CORS means link-only (`renderLinkList`), not a digested instrument or map layer — this alone has decided most of sas0's link-vs-instrument calls.
  2. **Reuse terms / license**: does the source's own terms of use actually permit republishing, not just viewing? (D51's news-org finding: readable ≠ reusable.)
  3. **Attribution requirements**: if the license mandates a specific citation format, use it verbatim — see D6's JMA citation (`出典：気象庁ホームページ　（当該ページのURL）`) as the template for "don't reword a legal citation requirement."
  4. **The two-axis check above** (open access × wants-to-be-aggregated) — run both, don't stop at one.
  5. **Provenance**: is this an official government/agency/research-institution source, or does it mix in unmoderated/anonymous crowd submissions? sas0 has never integrated the latter kind (D67 declined クママップ on exactly this basis) — flag it explicitly as a scope question for the user rather than deciding it unilaterally, since it's a values call, not just a technical one.
- **Respect for protected information and the missions that handle it.** sas0 deliberately stays out of the way of real EOC/command-and-control/incident-management systems (README's "What is not sas0?"). When writing anything user-facing — an instrument description, a doc, a commit message — don't imply this project has, needs, or should have access to operational/restricted systems, and don't understate what's actually at stake for the real missions it deliberately doesn't touch.
- **Why Open MCT specifically** is not incidental — see [DECISIONS.md](DECISIONS.md) D16. Keep that framing (NASA's own mission-control engine, reused unmodified for open civilian data) in mind when it's relevant, rather than treating Open MCT as an interchangeable dashboard library.
- **User-facing text is Japanese**, including instrument names, descriptions, and UI copy — this project's primary audience reads Japanese, and mixing languages in the running UI reads as unfinished. Proper nouns that are genuinely names (e.g. "Spiccato") stay as-is. This repo's own docs (README/DECISIONS/HANDOVER/CLAUDE) stay in English by prior decision — the language split is by audience (docs = maintainers, UI = end users), not inconsistency.

## Before making changes

- **Read [DECISIONS.md](DECISIONS.md) before touching `docs/index.html` or `docs/core.js`.** The Open MCT bootstrap has several non-obvious constraints (CDN version pinning, `SharedWorker` disabling, the standard vs. headless start path) that silently produce a blank page if violated. This isn't hypothetical — the PR that introduced this code shipped broken in exactly these ways.
- **Open MCT's native Telemetry API / Plot view is unproven in sas0 and was abandoned once already (D53).** Every sas0 object is pre-registered through custom `objects`/`composition` providers rather than Open MCT's own `+Create` flow, and wiring a hand-registered object into the real Plot view hit an apparently-unresolved internal rendering gap — metadata, composition, and `request()` all confirmed correct, but nothing ever drew, and enabling point markers threw a bundle-internal error. If a future telemetry-shaped instrument (アメダス, GEONETの座標値) tempts you toward `openmct.telemetry.addProvider`/`openmct.plugins.Plot()` again, read D53 first and budget time for the same wall, or just use a plain SVG/canvas chart via `registerInstrument` like `quake-trend.js` does — same data, no framework fight.
- Keep the scope minimal. The founding brief for this project explicitly rules out building an EOC, command-and-control software, chat/social software, workflow engines, databases, backend services, or auth/user management — see README's "What is not sas0?" section. When in doubt, prefer not adding a feature.
- **To add a new instrument**: create `docs/instruments/<name>.js` calling `SAS0.registerInstrument({ key, name, parentKey, render })` (an optional `order` controls position when the default registration order isn't what you want — D28), add a `<script>` tag for it in `docs/index.html` *before* `boot.js`, and add any config it needs to `docs/config.js`. Only add a new organization/grouping folder (`SAS0.registerFolder({ key, name, parentKey })` in `docs/folders.js`) when it will hold 2+ instruments — a folder wrapping exactly one instrument is a wasted click and gets dissolved on sight (D43); a single-source org just registers its instrument with `parentKey: 'root'` (or `'reference'` for occasional-reference sources) directly. See [DECISIONS.md](DECISIONS.md) D10. Note that "2+ instruments" is necessary but not sufficient — 気象庁 held 6 and still got dissolved in D54 because the frequently-used items inside it were worth a one-click promotion to root; a folder is a real usability cost, not a free organizational nicety, so don't assume one earns its keep just by clearing the instrument-count bar.
- Set `autoRefresh: false` on `registerInstrument()` for anything the user actively interacts with (an embedded map, an iframe) — the default periodic re-render (D10) will otherwise reset it mid-use. Only data-driven instruments (a fetched image, a fetched list) should auto-refresh. If `render()` holds a resource that needs explicit teardown (a WebGL context, a timer), return a cleanup function from it — `registerInstrument` calls it on `destroy()` (added for 状況図's MapLibre instance, D27).
- **Data that can be drawn on a map goes on 状況図 (`docs/instruments/hkd-map.js`, named 地図 until D48), not its own tree instrument — but only if it's genuinely live/overlay-shaped data, not reference material.** The tree/folder structure (D10) is for what can't or shouldn't be overlaid — warning lists, quake logs, volcano tables, and (per D46) reference documents like municipal hazard maps, even when a given one happens to be an interactive web map itself. D46 surveyed all 179 municipalities' hazard-map pages and found most aren't good overlay candidates anyway (inconsistent formats, static reference content) — don't take "it's a map" as a reason to pull something onto 状況図; ask whether it's live status first. Point layers (quake epicenters, volcano locations, D47; 電子基準点/GEONET locations, D53) are fair game when they reuse data another instrument already fetches (or a source with the same open/CORS character as the rest of the map) — no new source needed. See [DECISIONS.md](DECISIONS.md) D13, D26, D46, D47, D53.
- **When adding or recoloring a 状況図 layer, check the new color against *every* existing layer's paint values, not just the one you're building on top of.** アメダス's color collided with 電子基準点's blue (D60), got fixed, then turned out to also collide with 火山's calm/warning colors (D70) — twice in a row a new layer reused a color that read fine against its own immediate neighbor but not against the full set. `hkd-map.js`'s color constants (`SEVERITY_COLOR`, `CALM_COLOR`, `AMEDAS_COLOR`, 電子基準点's `#2f6fe0`, 地震's `#f5c542`) are the full palette in use — grep for them before picking a new one.
- Any new instrument source URL (image, iframe, etc.) needs a corresponding `allowedHosts` entry in `docs/config.js` and must go through `SAS0.getSafeUrl()` — don't assign to `.src` directly. See [DECISIONS.md](DECISIONS.md) D7.
- Before committing any change to a hardcoded external URL (a CDN pin, a placeholder image, an embed target), verify it actually resolves: `curl -sI <url>`. Several of the bugs fixed in this repo's history were exactly this — a URL that looked right but 404'd.
- **When picking up this repo after a gap, or after adding several new outbound links in one session, run `./scripts/check-links.sh`** to re-verify every URL in `docs/config.js`/`docs/instruments/*.js` still resolves — links added correctly can still go stale later (a page moves, a site restructures). A weekly GitHub Actions run (`.github/workflows/check-links.yml`, D45) does this automatically and files/updates a tracking issue on failure, but re-running it by hand after a batch of changes is still worth doing rather than waiting for the next scheduled run. A `FAIL` isn't automatically real: the script itself now skips five known-permanent false positives — base URLs for runtime concatenation (`warnings.js`'s JMA URL template, `weather.js`'s `imageBaseUrl`, `hkd-map.js`'s `REFERENCE_POINT_TILE_URL`/`AMEDAS_MAP_BASE_URL`, D22/D68) plus one XML namespace identifier that was never a URL to begin with (`quake-trend.js`'s `SVG_NS`, D68) — and retries once before reporting a real `FAIL`, but some sites still bot-block plain `curl` even when fine in a real browser (D20's river.go.jp). If a *new* hardcoded base-URL constant or namespace string gets added to an instrument, expect it to show up as a fresh false-positive `FAIL` next run — add it to `known_templates` rather than treating it as a real dead link. See [DECISIONS.md](DECISIONS.md) D22 for the full original reasoning (including why client-side/automatic detection isn't used instead), D45 for the CI addition, and D68 for the latest two-plus-one additions.
- `docs/index.html` currently pins Open MCT to a release candidate (`4.3.0-rc1`, D8) even though a final release newer than it now exists: `openmct@4.3.1` is confirmed live on unpkg as of 2026-09-05 (both `dist/openmct.js` and `dist/espressoTheme.css` resolve). Not yet bumped, not yet tested — see HANDOVER.md's open item #6. Re-run D2's `curl -sI` checklist plus a full local smoke test (including the `'start'` event and `SharedWorker` behavior — see the cross-project Open MCT notes, D65/D69, now at `dwg7/cafebabe`) before bumping it.

## Local preview

No build step. Serve `docs/` directly:

```bash
cd docs && python3 -m http.server 8000
```

Then open `http://localhost:8000/index.html`. Check the browser console — Open MCT bootstrap failures are often silent beyond a generic thrown error, so console errors are the primary signal something's wrong.
