## Resolved since last handover

- **`check-links.sh`'s retry logic hardened (D72), because the weekly job was starting to cry wolf.** [Issue #6](https://github.com/dwg7/sas0/issues/6) reported a 今金町 503 that answered 200 on the very next manual request — the second no-real-harm tracking issue in ten days (after Issue #4/D68). Unlike D68's, this class has no cause in sas0's own code: 199 URLs checked weekly, mostly small municipal sites, makes at least one flaky host per run close to structural. The thing at risk wasn't a link, it was the signal-to-noise ratio of the notification — an issue that's noise every week eventually gets closed unread, and then the week a link genuinely dies goes unnoticed. Fixed with the smaller of two options: retries went from 2 attempts to 3 with 3s/9s backoff, and a new `is_transient()` skips retries entirely for definitively-dead statuses (404/410), retrying only 000/403/408/429/5xx — so real dead links are still caught on the first pass and the run doesn't get slower. Verified with a stubbed unit test of the retry state machine plus a full run: 213/213 OK in 1m49s. **The deliberately-deferred second option** (report only what fails two weeks running, using the tracking issue body itself as the state store — no new permissions, no `data` branch, so it stays clear of D57's repo-writing line) is recorded in D72 for if retries alone turn out not to be enough.
- **状況図 gained JMA's 降水ナウキャスト as a raster layer (D71) — its first continuous field, its first forecast data, and a time axis that needed no stored history.** Chosen after a review concluded sas0's horizontal expansion (more sources) is exhausted and recent decisions had become mostly corrections of earlier ones; this adds depth on 気象庁, the source sas0 already uses most, with no new organization to evaluate. Three things it unlocks: the map finally shows rain as a *field* rather than 226 AMeDAS point samples (the root cause behind D60/D70's repeated color collisions — points were standing in for an area phenomenon); a scrubber spanning −3h to +1h, built purely from the frames JMA already publishes, so 状況図 gets time travel **without** crossing D57's repository-writing line; and `targetTimes_N2.json` makes this sas0's first forecast information of any kind. **The trap worth knowing about**: JMA serves these tiles only at *even* zoom levels — odd zooms return a perfectly valid HTTP 200 PNG that is completely empty, so nothing errors anywhere and the layer just silently draws nothing. At tileSize 256 MapLibre requests `mapZoom + 1`, so 状況図's default zoom 6 was fetching empty z=7 tiles; found only by reading the PNG chunk structure (data tiles carry `PLTE`/`tRNS`, empty ones don't) and confirmed at two independent locations across z=3–10. Fixed by pinning the source to `minzoom: 6, maxzoom: 6`. See [DECISIONS.md](DECISIONS.md) D71 — and note the general lesson: for tile sources, `curl` returning 200 proves nothing; verify pixels actually render.

- **[Issue #3](https://github.com/dwg7/sas0/issues/3) ("Define the SAS0 Exchange Model") is being untangled in DECISIONS.md as the discussion develops — no comment posted yet, nothing implemented.** The issue conflates two different things: sas0 *exporting* its own digested data (cheap — sas0 already builds GeoJSON `FeatureCollection`s internally for every 状況図 point layer) versus other systems *importing* into sas0 (which would require sas0 to become a backend with auth/ingestion/trust-moderation of non-government content, directly contradicting README's "What is not sas0?" and D17's open-data-only boundary). The design converged on "publish versioned, read-only GeoJSON; let the consuming dashboard interpret it — don't build an API," explicitly framed as RSS-like syndication (one-directional by definition, which implicitly settles the import question without a separate policy statement) rather than an exchange protocol. ## Open design thread: mappable vs. non-mappable data

A guiding principle surfaced during this work ([DECISIONS.md](DECISIONS.md) D13): the tree-of-instruments approach here is meant for data that **can't** be overlaid on a map (warning lists, quake logs, volcano tables, link cards). Data that **can** be represented as a map layer should instead be composited onto one shared map, classic-GIS "overlay everything" style — not fragmented into more non-map tree instruments. This is now realized in code, not just a design note: polygons as a *依代* (linking anchor), not information in themselves — a warning-region polygon's fill color comes from `warnings.js`'s own live data; a municipality polygon's click behavior jumps to its existing `config.js` hazard-map link. See D26 (the two Hokkaido-only vector-tile layers, live on `~/stars`) and D27 (状況図, the instrument that consumes them — named 地図 until D48).

**Resolved**: whether the 179 municipalities' actual hazard-map content (PDFs, web maps) should get pulled into 状況図 as overlay layers — no. The format survey (D46) found 56% are PDF-only and the remaining web maps split across ArcGIS/OpenLayers/Leaflet/bespoke JS with no shared base to integrate against; more fundamentally, this content is reference material (checked once, in calm weather), not live status — overlay is a tool for integrating *current* state spatially, not for shelving reference documents. 状況図 stays scoped to what's actually live (warning severity) and what's a linking anchor (municipality polygons → 市町村's existing links), and 市町村 (リンク集) keeps carrying the reference content. This settles that half of the original open question.

**Partially resolved**: 状況図 now also carries quake epicenters and volcano locations as point layers (D47), reusing `quake.js`/`volcano.js`'s own already-fetched JMA data — no new source needed — a third point layer of 電子基準点 (GEONET) locations from GSI's own CORS-open tile GeoJSON (D53), and a fourth of Hokkaido's 226 AMeDAS stations colored by precipitation (D59, a genuinely new source but confirmed CORS-open and folded into the map rather than becoming a new root instrument; recolored twice — D60, then D70 — chasing collisions with 電子基準点 and then 火山's own colors). A companion survey (D47) found every other still-link-only source (強震モニタ, 北海道開発局ポータル, 北海道 旅の安全情報, and their own referenced RSS/XML feeds) architecturally can't become digested instruments — no CORS anywhere outside JMA's `bosai` API and GSI's tile endpoints, and kmoni is additionally blocked by having no HTTPS at all. D48 promoted it to root position 1 (ahead of 気象庁) and renamed it 地図 → 状況図 to match this broader role — see D48.

**Still open**: GEONET's own 日々の座標値 (daily coordinate values, crustal deformation) was long listed as the leading further-out candidate — free/unregistered but a compressed proprietary text format needing a hand-written parser, a bigger lift than アメダス. **D73 proposes dropping it from sas0 entirely** (weekly updates with a three-week lag don't fit a situational-awareness product; hand it to sas1) — a proposal the user has not ruled on, see open item 12. Also open: whether `warnings.js`'s own digested data needs anything more on the map beyond the existing region-fill styling, and whether Open MCT's native Plot/telemetry API can ever be made to work for a hand-registered (non-`+Create`) object — D53 hit a wall here that wasn't resolved, just worked around. Two further ideas have a fully documented concept/feasibility (D57) and are still unbuilt, now with D73's triage attached: a GitHub Actions job accumulating 警報/地震/火山 state-change snapshots on a separate `data` branch (feasible, but sas0's first repo-*writing* workflow — a deliberate line to cross, and D73 found it is the same deliverable as Exchange Model v0 rather than a separate one; open items 9/10), and linking 状況図's 電子基準点 points to GSI's individual survey-result page (the polished page is unreachable — opaque undocumented URL encoding — and the unofficial JSON endpoint that does work is undocumented and could break without notice, which is why D73 proposes retiring this one; open item 11).

6. ~~Open MCT was pinned to a release candidate (`4.3.0-rc1`, D8)~~ — resolved 2026-09-13, see D74. Bumped to the final `4.3.1` release after re-verifying D2's checklist (both asset URLs 200) and a full local smoke test (bootstrap, router `'start'` navigation, 状況図's MapLibre/WebGL/nowcast rendering, 巡回モード, D4's harmless error still present but unchanged). No regressions found; only `docs/index.html`'s two version strings changed.
7. **北海道防災ポータル / さっぽろ防災ポータル / 川の防災情報 stay links, not digested instruments, because none of their JSON sends `Access-Control-Allow-Origin`** (D20) — re-checked 2026-08-29 (D45), still no CORS on any of the three. If any of them ever adds it, building a proper instrument for it (river levels and/or evacuation orders/shelters — the two things not covered anywhere else in sas0) would be a genuine upgrade over today's link.
8. ~~Whether to add a scheduled CI-based link checker~~ — decided, see D45. `.github/workflows/check-links.yml` runs `scripts/check-links.sh` weekly (plus `workflow_dispatch` for manual runs) and files/updates a tracking issue on failure — sas0's first CI, deliberately scoped to link-checking only, not touching build or deploy.
9. **The harvester (D57-1) is designed but unbuilt, and crossing its one line needs the user's explicit go-ahead.** A scheduled GitHub Actions job that fetches 警報/地震/火山 every 15–30 min and appends state-change events to a `data` branch, so changes that happen while nobody has the site open stop being lost (today's 更新情報, D53, can only diff against the last time *this browser* looked). Feasibility is settled — `raw.githubusercontent.com` serves any branch with `Access-Control-Allow-Origin: *` (verified), so the client can read it back with no backend, and the diff logic is a re-implementation of `change-log.js`. What's *not* settled is the decision itself: this would be sas0's **first workflow that writes to the repository** (`contents: write`), where `check-links.yml` only ever files issues. D57-1's own conclusion is that this permission expansion gets re-confirmed with the user immediately before implementing, not assumed from the design being ready.
10. **Exchange Model v0 (D61–D64) is specified but unbuilt — and per D73 it is the same deliverable as item 9, not a separate one.** Design is closed: publish versioned read-only GeoJSON/JSON at a stable URL ("syndication, not an API"), `source` required per feature, `retrieved_at` on the feed envelope, 警報・注意報 only for v0. It was blocked all along on having any stored history to publish, which is exactly what item 9 produces. **When item 9 is built, give its output those two D64 fields from the start and one implementation satisfies both.** One conflict to resolve at that point: D64 scoped v0 to 警報 only, while D57-1 snapshots 警報/地震/火山 — D73 suggests following D64's minimum-scope principle and starting with 警報. [Issue #3](https://github.com/dwg7/sas0/issues/3) is closed (the design was posted as a comment), so there's no open issue tracking this.
11. **D57-2 (linking 状況図's 電子基準点 points to GSI's individual survey-result page) — D73 proposes retiring this; the user has not ruled on it.** The only reachable endpoint is one found by watching the SPA's own network traffic (`service.gsi.go.jp/kijunten/app/api/base/{code}`), it's undocumented and could break without notice, it renders as raw JSON rather than GSI's actual page, and the hover panel already shows 点名/基準点コード/成果状態 — so the upside is small and the fragility real. Recorded as a proposal, not a decision: retiring it means withdrawing part of D57, which should be agreed explicitly.
12. **GEONET's 日々の座標値 (crustal-deformation time series) — D73 proposes moving this out of sas0 to sas1; the user has not ruled on it.** Long listed as the leading Phase 2 candidate. Free and unregistered, but a compressed proprietary text format (`.TRP.gz`) needing a hand-written parser — a bigger lift than anything sas0 has built — and updated weekly with a three-week lag. D73's argument for dropping it is definitional rather than technical: three-week-old data doesn't belong in something called *situational awareness*. The crustal-deformation angle is genuinely good for Hokkaido earthquake preparedness, so the proposal is to hand it to sas1, not discard it.
